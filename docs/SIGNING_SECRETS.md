# Signing Credential Interface (M10 Phase 16)

Signing credentials come ONLY from secure environment / CI secrets. **No
credential value ever appears in this repository, in logs, or in this
document** — only the exact secret variable names and their purpose.

## Already wired (updater signing — used by every release build)

| Secret variable | Purpose | Used by |
|---|---|---|
| `TAURI_SIGNING_PRIVATE_KEY` | minisign private key for Tauri updater artifacts (`.sig` files) | `.github/workflows/release.yml` (all packaging jobs) |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | password for the minisign key | same |

These are stored as GitHub Actions secrets on the repository. The local
updater key lives at `~/.jarvis/keys/updater.key` (mode 600, never printed,
never committed).

## macOS Developer ID signing + notarization (pipeline wired, NOT yet signed)

**Current state: `SIGNED: NO` / `NOTARIZED: NO`.** The workflow steps exist and
the credentials do not. With `MACOS_DEVELOPER_ID_CERT_P12` and
`MACOS_DEVELOPER_ID_CERT_PASSWORD` absent, `.github/workflows/release.yml` logs
`Signing: skipped (credentials not configured)` and the build is byte-for-byte
the unsigned one we ship today.

| Secret variable | Purpose |
|---|---|
| `MACOS_DEVELOPER_ID_CERT_P12` | Developer ID Application certificate (.p12, base64) |
| `MACOS_DEVELOPER_ID_CERT_PASSWORD` | .p12 export password |
| `KEYCHAIN_PROFILE` | `notarytool` keychain profile name (or use the three vars below) |
| `APPLE_ID` | Apple ID for `notarytool` (alternative to the keychain profile) |
| `APPLE_APP_SPECIFIC_PASSWORD` | app-specific password for `notarytool` |
| `APPLE_TEAM_ID` | Apple Developer Team ID |

### Generating the values

**.p12** — on the Mac whose login keychain holds the certificate:

```sh
security find-identity -v -p codesigning     # expect: "Developer ID Application: <name> (<TEAMID>)"
security export -t identities -f pkcs12 \
  -k ~/Library/Keychains/login.keychain-db \
  -P '<choose a password>' -o developer-id.p12
base64 < developer-id.p12 | tr -d '\n'       # paste as MACOS_DEVELOPER_ID_CERT_P12
```

`MACOS_DEVELOPER_ID_CERT_PASSWORD` is the `-P` password you chose. The export
carries the Developer ID and Apple Root CA intermediates with it, so the runner
needs no other certificates.

**App-specific password** — appleid.apple.com → Sign-In and Security →
App-Specific Passwords → generate → `APPLE_APP_SPECIFIC_PASSWORD`. Never reuse
the Apple ID password.

**Team ID** — developer.apple.com → Membership → Team ID → `APPLE_TEAM_ID`.

**`notarytool` profile** (optional; takes precedence over the three vars):

```sh
xcrun notarytool store-credentials "jarvis-notary" \
  --apple-id you@example.com --team-id <TEAM_ID> --password <app-specific-password>
```

Then set `KEYCHAIN_PROFILE=jarvis-notary`.

### How the pipeline is wired

1. **Signing: setup (Phase 14)** — with both cert secrets present: creates an
   ephemeral keychain under `$RUNNER_TEMP` (random password, never a secret),
   imports the .p12, adds the keychain to the user search list, resolves the
   identity, exports `APPLE_SIGNING_IDENTITY` + `SIGNING_ACTIVE`. Without them:
   skip log, exit.
2. **Build app + DMG** — Tauri picks up `APPLE_SIGNING_IDENTITY` and signs
   inner→outer with `--options runtime` (sidecar/frameworks, then the outer
   `.app`). `APPLE_CERTIFICATE` is deliberately *not* set, so Tauri creates no
   keychain of its own; notarization secrets are *not* exported here either, so
   Tauri's built-in notarizer stays off and step 4 owns notarization.
3. **Verify code signature (Phase 14)** — `codesign --verify --deep --strict`,
   then asserts `Authority=Developer ID Application` and `flags=.*runtime`.
4. **Notarize + Gatekeeper (Phase 15)** — `notarytool submit --wait`,
   `stapler staple` + `stapler validate`, `spctl --assess` on the `.dmg`
   (`--type install`) and on the `.app` (`--type execute`). Without notarization
   secrets: `Notarization: skipped (credentials not configured)`.
5. **Cleanup temporary signing keychain (always)** — `if: always()`; deletes the
   ephemeral keychain even when an earlier step failed.

### Shell sidecar

`apps/desktop/src-tauri/binaries/jarvis-core-<host-triple>` is a POSIX shell
launcher generated by `packages/core/scripts/build-core-runtime.mts`, not a
Mach-O binary. codesign accepts it (`Format=generic`) and `codesign --verify
--deep --strict` validates it inside the bundle, but macOS does not enforce
script signatures on execution and notarization only demands hardened-runtime
signatures for Mach-O code. The sidecar's integrity therefore comes from the
outer `.app` seal, which `--deep --strict` checks. Documented, not worked around.

## Windows Authenticode signing (pipeline wired, NOT yet signed)

**Current state: `WINDOWS_SIGNED: NO`.**

| Secret variable | Purpose |
|---|---|
| `WINDOWS_PFX` | Authenticode code-signing certificate (.pfx, base64) |
| `WINDOWS_PFX_PASSWORD` | .pfx password |

Generate the base64 value from the .pfx (PowerShell):

```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes('jarvis-codesign.pfx'))
```

The workflow decodes `WINDOWS_PFX`, imports it into `Cert:\CurrentUser\My`,
takes the thumbprint and injects `certificateThumbprint` / `digestAlgorithm` /
`timestampUrl` / `tsp` into `bundle.windows` via `--config` **during** the NSIS
and MSI builds. Signing must happen before bundling finishes, because the
updater `.sig` is computed over the final installer — signing afterwards would
invalidate it. Tauri then signs the sidecar `.exe`, `jarvis-desktop.exe` and the
installers. Verification in CI uses the built-in `Get-AuthenticodeSignature`
(`Valid`); for a manual check use `signtool verify /pa /all <installer>`. When
either secret is absent the build config passed to Tauri is exactly the one we
pass today.

## Rules

- Secrets enter the pipeline ONLY via `secrets:` context — never committed,
  never logged, never echoed.
- Honest current state: `MACOS_SIGNING_PIPELINE_READY: YES`,
  `MACOS_NOTARIZATION_PIPELINE_READY: YES`, `WINDOWS_SIGNING_PIPELINE_READY: YES`
  — and `MACOS_DEVELOPER_ID_SIGNED: NO` / `MACOS_NOTARIZED: NO` /
  `WINDOWS_SIGNED: NO`. The steps exist; the credentials do not.
- Never fabricate a SIGNED/NOTARIZED verdict.
